# 健康管理アプリ（パーソナル食事・健康・筋トレ・サプリ管理）

本人専用の健康管理アプリ。医療診断は行わず、事実の整理・提案・必要時の受診促しに徹する。
体重・体組成の記録を中核機能とし、食事・間食・飲酒・筋トレ・サプリ・健診データを一元管理する。

詳細な要件・画面設計・データ構造・AI判定ルール・医療安全ルールは元の引継ぎ資料を参照。

## 同梱アプリ

このリポジトリは Vite のマルチページ構成で、4つのフロントエンドをビルドする。

| ページ | 内容 |
| --- | --- |
| `index.html` | 健康管理アプリ（食事・健診・筋トレ・サプリ・体重） |
| `mortgage.html` | 住宅ローン 金利シナリオ・シミュレーター |
| `sasaoka.html` | 仕切り計算・請求書作成（笹岡工務店）※1ファイルにビルドして太陽ポータルに置く |
| `jutaku.html` | 住宅改修 見積書作成 ※1ファイルにビルドして太陽ポータルに置く（仕切り計算・請求書作成とデータを一緒に使う） |

開発サーバー起動後は `http://localhost:3000/`（健康管理）と `http://localhost:3000/mortgage.html`（シミュレーター）でそれぞれ開ける。
公開後は `https://<ユーザー名>.github.io/<リポジトリ名>/mortgage.html`。

### 住宅ローン 金利シナリオ・シミュレーター

変動金利が段階的に上昇した場合に、月々返済額・残高・総返済額がどう変わるかを試算し、
**金利と総返済額の相関**をグラフで確認するための単体アプリ（Firebase 非依存・入力値はサーバーに送らない）。

- 借入額・返済期間・当初金利・見直し間隔・上昇幅・上限金利をその場で変更して再計算
- 「金利と総返済額の相関」グラフは、X軸を「見直しごとの上昇幅」と「全期間固定金利」で切り替え可能
- 累計利息 / 残高の推移、月々返済額の階段状の推移、区間ごとの内訳表
- 125%ルール（返済額の上昇を直前の1.25倍までに抑える）を有効にすると、未払利息と最終回の一括精算まで追跡する
- 条件はURLのクエリ（`?p=3300&y=35&r=1.25&s=0.25&rv=5&max=10&cap=0`）に反映されるため、そのまま共有できる

計算ロジックは `src/mortgage/calc.ts`（元利均等返済・見直しごとの返済額再計算＝いわゆる「5年ルール」に近い方式）。
上昇幅やタイミングは想定の一例であり、実際の適用金利・ルール・諸費用は金融機関によって異なる。

  原本には前の申請の丸が残っていた（みやこ町は4枚とも①、広域連合は②の用紙だけ②）ので、それは消してから描く。箇所のない写真番号の用紙は丸なし。プレビューにも出る。
  **縦書きの欄**（ユーザーの指示「縦で入力できるようにする」）：原本で文字の方向が縦書きの欄（写真貼付用紙の改修の種別①〜⑥・内訳明細書の「写真番号」・理由書の「利用者」など）は、
  プレビューでも1文字ずつ下へ積んで描く（Excel の縦書きと同じく、文字の向きは横のまま。縮小して全体を表示の欄は縦の長さで縮める。前は横書きで描いていて、狭い欄からはみ出していた）。

  **平面図の工事内容**（ユーザーの指示「平面図の空いたスペースに工事内容の詳細を記入する。平面図はこちらで作成する」）：平面図の空いた所に、申請書の改修の内容と同じ行（「①浴室　手すりの取り付け　L=600mm」）を1行ずつ書く。
  苅田町・行橋市（平面図  (2) の C54:AQ68）・広域連合（平面図 (2) の B37:H52）は、前の申請と同じ所に線・塗りなしのテキストボックス（12pt。入らなければ小さくする。Excel で動かせる。行が多くても隠さない）、
  みやこ町は平面図の下の欄（M48。折り返しの書式）。苅田町・行橋市の平面図の表題（C2）に氏名も入れる。平面図そのもの（横棒＝横手すり、丸＝縦手すり、番号）は Excel で描く。
  見積もりの入口の「📥 申請書（Excel）から作る」はユーザーの指示（「不要」）で外した（書いた申請書を読む `readShinsei` は、テストで読み戻すのに使う）。
- **笹岡工務店の請求書に入れる**（見積書の上の、保険者・担当と同じ枠。様邸の `shikiri`）：見積書に行をはじめて入れたときに入る（新規作成は申請書と見積書の両方なので、申請書だけの様邸は入れない。前から行のある見積書は変えない。`startEstimate`）。
  見積書に行がないうちはこのチェック自体を出さない（前から入れてある様邸は、外せるように出す）。複製は見積書があれば入れる。入れると請求する月が出る（施工日は請求書を確認するの様邸で）。
  入力の画面には請求書に入る金額を出さない（ごちゃごちゃするので。金額は「🧾 請求書を見る」でその様邸の仕切り計算表を開いて見る。部材代は見積の単価ではなく仕切価格）。
  仕切価格が空欄の部材があるときだけ知らせ、その場で入れられる（部材リストの仕切価格も同じにできる）。
  「請求書を確認する」の一覧・請求書には `shikiri` の様邸だけが入る。外すときは見積書のチェックを外すか、仕切り計算の「請求書から外す」（見積書は残る）。「削除」は見積書からも消える
- **見積書と請求書の行き来**（`links.ts`）：仕切り計算の「📝 見積書を開く」、見積書の「🧾 請求書（仕切り計算表）で見る →」でタブを変えて同じ様邸を開く。
  請求書を確認するの様邸の画面の左上は「← 見積もりへ戻る」（その様邸の見積書を開き、請求書のタブは一覧に戻しておく。ユーザーの指示）。請求書の一覧へは「🧾 請求書を確認する」のタブで戻る（請求月を変えていたらその月）。
  開いているタブ・様邸は URL に `#tab=…&job=…` で残す（読み直しても同じ所。前の版の `#job=…` は最初のタブで開く）
- **保存**：打ち込むたびに自動で保存する（少し待ってから。画面を閉じる・ほかのタブやアプリに移るときはすぐ）。見積書の画面の「💾 保存」（Ctrl+S でも）はすぐ保存して知らせる
  （欄に打ち込んでいる途中なら、その値を入れてから保存する。`useStore.ts` の `flush` は保存できたら true）。
- **📗 Excel で保存**（`estimateXlsx.ts`・`xlsxWrite.ts`）：見積書の画面の「📗 Excelで保存」と一覧の「📗 Excel」で、印刷する見積書と同じ形の .xlsx をダウンロードする
  （ファイル名は「山田花子様住宅改修見積書.xlsx」。ユーザーの指示、2026-10-22。前は「工事費見積書兼工事費内訳書_山田様_2026-10-20.xlsx」）。列の幅・行の高さ・罫線（数量と単位の間は線なし・太い線）・結合・文字の大きさ・
  ヘッダー（作成日）とフッター（ページ・福岡県介護保険広域連合）・A4横・余白は印刷と同じ（寸法は `print/formLayout.ts` を印刷と共有）。ページは下へ並べて改ページを入れる
  （「1ページに合わせる」にすると Excel は改ページを使わないので、倍率で幅に入れる）。長い文字は「縮小して全体を表示」、2行の欄は折り返し。
  金額は元の Excel と同じく式（金額＝ROUNDDOWN(数量×単価,0)、介護保険の対象の欄は左と同じ、小計＝SUM、諸経費・消費税は ROUNDDOWN）にし、計算済みの値も入れる。
  式の答えがアプリの金額と違う行（1m÷3m のように割り切れない数量を 0.333 と書く行など）と、手で直した諸経費・端数調整した諸経費は数字のまま書く（単体テストで全部の式を計算し直して確かめる）。
- **🛒 発注書**（`order.ts`・`estimate/OrderPage.tsx`・`print/OrderDoc.tsx`）：見積書の画面の「🛒 発注書を作成」で、見積書に入っている部材を「何を何個（何本・何枚）発注するか」にまとめる
  （見積書に行がないうち＝申請書だけの様邸は押せない。URL の `view=order` で開いても見積書を出す）。
  同じ部材（メーカー・品番・品名が同じ）は箇所をまたいで足す。施工費・空白の行・金額だけの行は入れない。規格品をそのまま使う部材は見積書の数量のまま。
  切って使う部材（マツ六の手すり BD-134・ベースプレートなど、1本の長さと使う長さの入った部材）は、使う長さを足して 1本の長さ（4000mm）を何本発注するかにする：
  同じ1本から切れるものはまとめ（長いものから順に入る1本に入れる）、半分の長さ（2000mm）で足りる1本は 2000mm に、余り（発注する長さ−使う長さ）が 0.1本（400mm）より少なければ危ないので 2000mm をもう1本。
  例：600mm×2＋1600mm×1＝2800mm（0.7本）→ 4000mm 1本（余り 1200mm）、1600mm（0.4本）→ 2000mm 1本、3800mm（0.95本）→ 4000mm 1本＋2000mm 1本。
  発注書には何を何本かだけを出し、この計算の説明（使う長さ・余り・足す分）は出さない（画面・印刷・販売受注簿への転記とも）。
  2000mm の品は部材リストから探す（長さだけ違う同じ品。品番 BD-134→BD-132、HD5-4000→HD5-2000 も手がかり）。なければ品番・価格を空けて「確かめてください」と出す（1本の長さが 4000mm の部材だけ。ほかの長さで半分の品がなければ1本の長さで数える）。
  数は ＋／− で直し、✕ で消し（「消した行」から戻せる）、「＋ 部材リストから足す」で見積書にない部材を足せる（見積書にある部材は、その行の数が増える）。直したところは様邸の `order` に持つので、見積書を直しても残り、見積書から計算した数が変わった行には「見積書から計算した数は ○個 戻す」が出る。
  部材ごとに、どこで使うか（見積書の写真番号 ①②）を出す（画面と印刷のいちばん右の欄。見積書の写真番号を変えれば発注書も変わる。発注書で足した行は空）。
  発注先・発注日を入れて「🖨 発注書を印刷」（A4縦。数量と単位を大きく。品目数・現場の住所・備考は出さない）。URL のうしろの `&view=order` で、読み直しても発注書を開く。
- **📤 販売受注簿に転記**：販売受注簿作成ツール（taiyo-hacchu-scan リポジトリ。ポータルと同じサイトの `/taiyo-hacchu-scan/`）を新しいタブで開き、発注する部材を渡す
  （同じサイトなので、この端末の localStorage の `taiyo-hacchu-import-v1` に置く。品名・メーカー・品番・数量（1以上の整数）・単位・定価・仕切価格、お客様名・住所・営業担当（名字）・発注先）。
  開いた販売受注簿で「受注簿に入れる」を押すと、部材1点が商品ページ1枚になる（受け取る側は taiyo-hacchu-scan の `src/main.jsx` の `jutaku-import-begin`〜`end`）。
- 印刷：様邸ごとの明細（箇所ごとの表＋①〜⑦）と、請求書＋全様邸の明細のまとめて印刷（A4縦）、見積書（A4横）、発注書（A4縦）。印刷の画面で「PDFに保存」を選べばPDFにできる。スマホなど画面が狭いときは、印刷イメージを画面の幅に縮めて見せる（「拡大」で原寸。印刷は常に原寸）
- **データ**はこの端末のブラウザの IndexedDB（`taiyo-sasaoka-shikiri`）だけに保存（太陽ポータルのアプリは同じサイトで localStorage の容量を分け合うため、件数の多い部材リストは IndexedDB に入れる）。設定画面からバックアップ（JSON）の保存・読み込み、部材リスト・手間単価・部材＋施工費（常用）だけのファイルの受け渡しができる（どちらのアプリで保存しても両方の内容が入る）。
  2つのアプリ（とそのタブ）が同じ項目（様邸の一覧・部材リストなど）を使うので（`storage.ts`・`useStore.ts`・`sync.ts`）、保存のたびに項目ごとの印（`stamp:項目名`）を変える。
  もう片方が保存したら（BroadcastChannel の知らせ、画面に戻ったとき）読み直す。別の画面に移るときは待たずに保存する。
  保存するときに印が前に読んだときと違えば（もう片方が先に保存していた）、3つ（前に読んだもの・こちら・向こう）を比べ、様邸・箇所・行の項目ごとにまとめてから保存する（片方だけが変えたところはその方、同じ項目を両方で変えたときはあとから保存した方）

#### ビルド・公開

```
npm run build:sasaoka    # dist-sasaoka/index.html（仕切り計算・請求書作成。1ファイル・約4MB、JS・CSS・PDF読み取り用データ・申請書の原本を同梱）と version.json
npm run build:jutaku     # dist-jutaku/index.html（住宅改修 見積書作成。同じく1ファイル）と version.json
```

公開中：太陽ポータル（taiyo-portal リポジトリ）の `jutaku-mitsumori/index.html`（タイル名「住宅改修 見積書作成」）と `sasaoka/index.html`（タイルはなく、アプリの請求書のタブから開く）。
直したときは、このブランチでビルド → `dist-sasaoka/` の `index.html` と `version.json` を taiyo-portal の `sasaoka/` に、`dist-jutaku/` の2つを `jutaku-mitsumori/` に上書き → taiyo-portal の master に push（GitHub Pages が自動で公開する）。
`version.json` はビルドした日時（`vite.version.ts`。アプリにも同じ印を埋め込む）。スマホのブラウザは前に開いたページをしばらく覚えていて直した版がすぐ出ないことがあるので、アプリは開いて少ししてからと画面に戻ったときに `version.json` を見て、印が違えば上に「このアプリの新しい版が出ています ⟳ 読み込み直す」を出す（`update.ts`。保存してから読み込み直す）。
2つは必ず同じサイトに置く（別のサイトだとデータ（IndexedDB）が別になり、部材リストも請求書も連動しない）。ポータルと同じサイトなので、ポータルで選んだ営業所（`localStorage` の `taiyo_portal_session`）を発行元・施工業者に使う。
パソコンに保存したファイルで開いたときのデータは、ポータルのデータとは別（移すときはバックアップを使う）。

## 技術スタック

- フロントエンド: React 19 + TypeScript + Vite（マルチページ）+ Tailwind CSS 4（GitHub Pagesでホスティング）
- グラフ: Recharts
- データ保存: **この端末のブラウザのlocalStorageにのみ保存**（サーバー・アカウント不要）
- ホスティング: GitHub Pages（静的サイトとしてビルドして配信）

サーバー・データベース・APIキーは一切使用しない。アカウント登録やログインも不要で、開いた瞬間から使える。

## セットアップ

**前提:** Node.js 20+

1. 依存関係をインストール
   ```
   npm install
   ```
2. 開発サーバーを起動
   ```
   npm run dev
   ```

環境変数の設定は不要（Firebase等の外部サービスを使わないため）。

## データの保存場所と制約

- すべてのデータ（体重・食事・サプリ・健診記録など）は、開いているブラウザの `localStorage` に保存される
- **別の端末・別のブラウザ・シークレットウィンドウでは、記録したデータは見えない**（この端末のこのブラウザだけのデータ）
- ブラウザの「閲覧データを削除」操作や、ブラウザの再インストールでデータは消える
- 設定画面の「データをエクスポート」でJSON/CSVとしてバックアップ可能。週1回程度のエクスポートを推奨

複数端末での同期や、AIによる食事テキストの自動解析（栄養素の自動入力）を使いたい場合は、Firebase等のバックエンドを別途用意する構成に戻すことも可能（過去のコミット参照）。

## 自動デプロイ（GitHub Actions）

`main` ブランチへのpush時に `.github/workflows/deploy.yml` がビルドしてGitHub Pagesに公開する。

初回のみ、以下を手動でセットアップする。

1. リポジトリの **Settings → Pages → Build and deployment → Source** を **GitHub Actions** に変更

これだけで、以降は `main` へのpush、または GitHub の Actions タブから `workflow_dispatch` で手動実行するとデプロイされる。
公開URLは `https://<GitHubユーザー名>.github.io/<リポジトリ名>/`。

## 実装範囲（MVP）

含む: 体重・体組成記録+推移グラフ、食事記録（テキスト入力→項目分割→手動確認）、よく食べるメニュー、間食管理、筋トレ記録、サプリ管理+重複警告、健診データ入力+前年比、ホームサマリ+改善提案（最大3件）、JSON/CSVエクスポート。

見送り（次フェーズ）: 食事内容のAI自動解析（栄養素の自動推定）、AIアシスタント自由対話、献立提案の高度化、週次レポート自動生成、健診前モード、音声/写真入力、目標体重に基づく自動ペース計算、複数端末間の同期。

## 医療安全上の注意

本アプリは診断を行わず、体重・数値の増減について断定的な評価（「肥満です」等）はしない。
症状トリガー（胸痛・息切れ・動悸・失神・浮腫）が入力された場合は必ず受診相談を促す。
薬・サプリの中止を指示することはなく、医師の指示を常に優先する。
