# 住宅改修 見積書・請求書アプリ（太陽シルバーサービス 行橋営業所）

介護保険の住宅改修で、営業所が作る見積書・笹岡工務店からの仕切り計算・1か月分の御請求書・部材の発注書を1つのアプリで作る。
ユーザーは行橋営業所の担当者（プログラマーではない）。スマホとパソコンの両方で使い、スクリーンショットに丸を付けて「ここを〜に」と頼んでくる。
このスキルは、2026年10月のセッションで積み上げた知識（何をどこで直すか・業務の決まり・確かめ方・公開の仕方・同じ失敗をしない工夫）をまとめたもの。
ポータル全体に共通のこと（アプリの一覧・公開の流れ・ユーザーの好み・報告のしかた）は `taiyo-portal` スキル、Excel の作り方と確かめ方（XSD・LibreOffice のスクリプト）は `taiyo-excel-export` スキルにある（入っていれば一緒に読む）。

## 仕事の進め方

1. **依頼を業務の言葉で読み解く。** 短い文とスクリーンショットで来る。例に計算の書き違いがあることもある（発注書の例「0.15本×2＋0.4本 → 2000mm を1本」は合計 0.7本＝2800mm で 2000mm に入らない）。
   その場合は、例の意図（少なければ 2000mm）を一般のルールにして作り、報告で「こう解釈した」と書く。細かいことを何度も聞き返すより、筋の通った解釈で進めて見せる方が喜ばれる。
   ただし、データを消す・外に送るなど取り返しのつかないことは確かめてから。
2. **関係する所をまとめて洗い出す。** 「当然、請求書や申請書にも転記する」のように、1つの直しがほかの出力（見積書の画面・印刷・Excel・仕切り計算表・請求書・発注書・販売受注簿）にも届くことを期待されている。
   直す前に `grep` で同じ値を使う所を全部見る。
3. **小さく直し、まわりのコードの書き方に合わせる。** コメントは日本語で「なぜ」を書く（このリポジトリの流儀）。画面の文字は短く、やさしい言葉で。
4. **確かめる。** 単体テスト・型チェック・ブラウザのテスト（Playwright）を通し、見た目を変えたらスクリーンショットを撮って自分の目で見る。スマホの幅（390px）も見る。手順は `references/build-test-publish.md`。
5. **公開する。** ユーザーが「公開して」と言ってから（本番。作業環境の安全確認で止められたら回り道をせず、ユーザーに聞く。`taiyo-portal` スキル）。
   2つのビルド（`build:sasaoka`・`build:jutaku`）の `index.html` と `version.json` を taiyo-portal の2つのフォルダに置いて push。ポータルのタイルの使い方の文（`taiyo-portal/index.html` の `APPS`）も、変えた所に合わせて直す。
6. **デプロイを確かめる。** github.io はこの作業環境から見えないので、GitHub MCP の `actions_list`（`pages build and deployment`）で success を見る。
7. **報告する。** 日本語・やさしい言葉で、①できたこと ②使い方（番号付き） ③確かめてほしいこと（解釈したところ・ユーザーのデータに要るもの） ④テストと公開の結果。スマホで古い画面が出たら上の「⟳ 読み込み直す」を押すように添える。

## ユーザーの好み（これまでの指摘から）

- 箇所の候補（箇所を足す・改修場所の候補）は苅田町の写真の用紙の改修箇所（□廊下…□玄関～道路）と同じ名前・順番にする（2026-10）。
- 言葉：「工賃」ではなく「**施工費**」。「一式」ではなく「**部材＋施工費（常用）**」。「手摺」ではなく「**手すり**」（2026-10。施工費・取り込む商品名・申請書とも。`util.ts` の `tesuri`）。
  改修の種類は「手すりの取付」ではなく「**手すりの取り付け**」（2026-10-21。`KINDS`。申請書の原本の文字も）。ボタンは「📋 部材リストから入れる」。長さは「600mm÷4000mm＝0.15」のように **mm を付ける**。
- 画面の説明文はいらない（ツールバーの下の説明は「この説明は不要」と言われて消した）。説明は README とポータルのタイルの使い方の文に回す。
  見積書の画面でも「見積書に直接入力（Excel と同じように…）」の見出し・元に戻す／やり直すのボタン・「お客様名…は見積書の欄に直接打ち込みます」・
  「2026年10月分の請求書に入る金額：①…⑥」・「（申請書を出す先）」などを「いらない。Ctrl+Z で元に戻す、Ctrl+C でコピー、Ctrl+V で貼り付けが使えればいい」と言われて外した（2026-10）。
  見積書の入口の説明の文も外した。お知らせ（トースト）も「保存しました」「行を消しました」のように短く、説明を付けない。
- 消す操作には確かめを入れる（「全部いきなり消えてしまうと結構困る」）。「📄 白紙に戻す」は「見積書を白紙に戻しますか？」と聞いてから消し、Ctrl+Z でも戻せる。
- **ボタンの色は控えめに。** 「削除・白紙に戻す・発注書作成などの色付けで目がチカチカする。色付けは Excel に保存と印刷くらいにして、濃い色は要らない」（2026-10）。
  保存＝`softBlue`・Excelで保存＝`softGreen`・印刷＝`softSky`（`ui.tsx` の薄い色）、ほかは `white`（削除も白。消す前の確かめで守る）。新しいボタンもこれに合わせる。
  **保存・Excel・印刷のボタンは上の段のまん中**（「Excelの印刷、保存ボタンを中央にもってくる」2026-10-22。申請書・見積書のタブとも、上の段を 左・まん中・右 の grid に。白紙に戻す・発注書・複製・削除は右）。
- フリガナはひらがな・半角カタカナで打っても全角カタカナにする（「ひらがなで入力しても、全角カタカナに自動的になるようにする」2026-10-22。`toKatakana`・`KanaInput`。変換中は変えない）。
  ただし見積書の上の「部材リストから入れる」「施工費から入れる」「部材＋施工費（常用）から入れる」は「ほんの少し色付けしてわかりやすく」と言われ、
  ごく薄い緑・水色・紫にした（2026-10-21。`sasaoka.css` の `.tool-material`・`.tool-labor`・`.tool-kit`）。
- **よく使う所は大きめに。** 見積書の上の 保険者・担当・見積もり作成日・請求書に入れる・請求する月 の欄と、部材・施工費を入れる3つのボタン、
  部材＋施工費（常用）の画面の「部材リストから入れる」「施工費を入れる」は「もう少し大きくする」と言われて大きくした（2026-10-21。文字 16px・高さ 44px ほど）。
- **仕切価格は 定価×0.8 ではない。** 空欄なら空欄のまま知らせる（「仕切り価格は0.8ではありません」。`business-rules.md` の7）。
- **諸経費は合計の末尾が0になるよう端数調整**（「諸経費は端数調整のために合計金額の末尾が0になるように」2026-10-22。`overheadAuto`）。
- **ファイル名は「○○様住宅改修申請書.xlsx」「○○様住宅改修見積書.xlsx」**（お客様名のすき間は詰める。保険者・日付は付けない。2026-10-22）。
- **商品名は長いときだけ言葉の切れ目で改行**（「適度に行替えをおこない、見やすくする。商品名が長い場合のみ」2026-10-22。`wordLines`）。
- 部材を選ぶ画面の「★ お気に入り」に「削除」（お気に入りから外す。部材リストには残る）。「お気に入りリストでも削除ボタンをつける」の指示。
- 請求書を確認するの様邸の画面の左上は「← 見積もりへ戻る」（「一覧へ戻るではなく、見積もりへ戻るへ変更」。その様邸の見積書を開く。一覧へはタブで戻る）。右の「📝 見積書を開く」は残した。
- 帳票にも計算の説明はいらない。発注書の品名の下の「使う長さ…→4000mm 1本＋2000mm 1本（余りが…）」「…の余りが少ないので足す分」は「＋分などの説明は不要です」と言われて消した。帳票は「何を何本・いくら」だけにする。
  その次に「〇〇までに納品など、不要な部分が入っています」とも言われ、発注書の備考・品目数・現場の住所も外した。頼まれていない欄・行を帳票に足さない（「など」と言われたら同じ種類のものをまとめて外す）。
- 行の操作は表の行の左のボタン：**「挿入」（下に1行）「✕」（消す）「コピー」**の順（「＋ボタンではなく、挿入とし」2026-10-21）。コピーしたら「貼付」で貼り付け。ツールバーに行の操作ボタンを並べない（不要と言われて消した）。
- 申請書の一覧は申請書の上からの順番だが、**被保険者氏名はフリガナのすぐ下**（「ふりがなの下に、名前をもってくる」2026-10-21）。生年月日の元号は**初めから昭和**（「昭和がデフォルトにする」）。
- Excel と同じ操作感（Enter で下、Tab で右、F2、Ctrl+Z／Y、Ctrl+C／X／V、Ctrl+Shift+＋、Ctrl+－、Alt+↓、Ctrl+S、Ctrl+P）。
- 見積書は役所の様式（いただいた Excel）の形のまま。枠の大きさは変えない。Excel ファイル（.xlsx）でも同じ形で保存できること。
- 進み具合は短く知らせる（長いこと黙らない）。

## 落とし穴（同じ失敗をしない）

- **画面が横に動く・ふるえる。** タブごとに画面の幅を変えない（前は見積もりのタブだけ 1600px で、広い画面でタブを切り替えると 100px 動いた。今は `App.tsx` の `PAGE_WIDTH` の1つ）。
  申請書のプレビューの箱は `scrollbar-gutter: stable`（スクロールバーが出たり消えたりして幅が変わり、幅に合わせて縮めるプレビューがふるえた）。
  画面全体（html）には付けない（付けると、印刷イメージ・部材を選ぶ画面など全面に出す画面の右に、覆われない帯が出る）。
  確かめるときは Playwright で `ignoreDefaultArgs: ['--hide-scrollbars']`（ふつうはスクロールバーが出ないので、この不具合が見えない）。2026-10-22

- **2つのフォルダの両方を更新する。** `jutaku-mitsumori/` と `sasaoka/` は同じアプリ。片方だけだと、もう片方の入口から古い版が出る。`version.json` も一緒に置く（新しい版の知らせに使う）。
- **ビルドで `package-lock.json` が書きかわる。** 依存を変えていなければ `git checkout -- package-lock.json`。
- **様邸（Job）に項目を足すときは3か所。** 型（`types.ts`。テストが Job を直接作るので、足す項目は `?:` の省略可にする）・読み込みの `cleanJobs`（書かないと読み直したときに消える）・複製の `copyJob`（引き継ぐか決める）。手順は `references/codebase.md`。
- **自動保存は打ち終わって 0.4 秒後。** テストで直してすぐ読み直すと消える（1.2 秒ほど待つ）。
- **常駐のサーバーは 2 時間で止められる。** テストのときだけ立てる `scripts/serve.mjs` を使う。
- **ほかのセッションも同じリポジトリに push している。** push を断られたら `git fetch` で中身を見て、自分のまだ push していないコミットを rebase。ビルドした成果物（ハッシュ名の assets）はマージせず、作り直す。
- **ワイルドカード付きの削除（`rm docs/assets/*` など）は安全確認で止められる。** 消すファイルは名前を1つずつ指定する（`git rm -f -- docs/assets/古い名前.js`）。
- **申請書の原本（.xltx）の文字・書式を直すときは、共有の文字（sharedStrings.xml）・styles.xml の決まった所だけを書きかえ、ほかの部品はそのまま zip し直す。**
  ふりがな（rPh の sb・eb）の位置も文字の増えた分ずらす。直した文字が欄の幅・高さに入るか（Excel の折り返し・縦書き）を計算と LibreOffice の描画で確かめる。
  LibreOffice は縦書きの「縮小して全体を表示」をしないので、縦書きの長い文字は原本の文字を小さくしておく（広域連合の写真貼付用紙の D6）。
- **申請書の欄は行数で文字の大きさが変わる**（`fitLines`）：改修の内容の欄の文字の大きさを決め打ちで確かめるテストは、箇所の数を変えると合わなくなる。欄に入るか（行×文字×1.25 ≦ 欄の高さ）で確かめる。
- **生年月日の元号は空でも昭和**（`eraOf`）：何も入れていない申請書でも元号の丸（苅田町・行橋市）・「昭和」の文字（みやこ町・広域連合）が出る。丸の数を数えるテストは、その分を足すか除く。
- **ユーザーの価格表（メーカーの PDF・Excel）はリポジトリに入れない。** テストには自分で作った見本を使う。
- **コミットの件名・本文にモデル名を書かない。** 末尾には、そのセッションで指示された2行（`Co-Authored-By: …` と `Claude-Session: …`）を指示どおりそのまま付ける。PR は頼まれたときだけ。
- **行の左にボタンを足すときは余白に注意。** 置き場所は見積書の左の余白だけで、今の3つでほぼいっぱい。前にあった「▲ 上へ／▼ 下へ」はユーザーの指示で外した。詳しくは `references/codebase.md` の4。
- **いただいた申請書・様式に、前の申請の名残り（別の方の氏名・番号・写真・平面図）が入っていることがある。** アプリは誰でも開けるので、そのまま入れない。
  全シート・図形・写真・共有の文字・外部リンクを調べて消し、消えたことを確かめ、何を消したか報告する（`business-rules.md` の11）。
- **ユーザーの「ダミー」「取り込まないで」と言われたファイルは、形を読むだけ。** アプリのデータにもリポジトリ・テストの見本にも入れない（見本は自分で作る）。
- **申請書の丸（楕円の図形）の位置は計算。LibreOffice の見た目で合否を決めない。** LibreOffice は列の幅を代わりの字体で計算するので半字ほどずれて見える。
  確かめるときは、原本に残っていた前の申請の手書きの丸・図形の保存位置（a:off）と計算を比べる（`business-rules.md` の11）。ずれていると言われたら、その欄の文字の幅（`P_WIDTH`）を見直す。
- **申請書の画面の欄の順番は、保険者ごとの申請書の上からの順番。** 欄を足すときは、原本で場所を確かめて `SHINSEI` の `texts` と `ShinseiEditor.tsx` の `FIELDS` の両方に入れる。
  プレビュー（申請書のタブ）の押せる欄は `SHINSEI` から作る（`shinseiPreview.ts` の `fieldRefs`。項目の名前を増やしたら `TEXT_FIELD` にも）。
- **申請書のプレビューは、Excel に保存するときと同じ書き込み（`fillFiles`）をしたシートを描く。** プレビューだけ別に書く所を作らない（ずれる）。
  原本の式は空の欄を参照すると「0」を出す（苅田町の申請者の住所・氏名・電話番号）。Excel と同じなので消さない。
  ブラウザのテストで欄を押すときは、開いている入れる所が下の欄にかぶるので Esc で閉じてから、欄の中の丸の値（「昭」など）でない所を押す（`e2e-shinsei.mjs` の `openSpot`）。
- **請求書・発注書は、見積書を作ったときだけ。** 笹岡工務店は、このアプリで見積書を作る（手入力の）工事だけ。ほかの工務店の工事は見積書が向こうから来るので、ここでは申請書だけ（ユーザーの話、2026-10-21）。
  新規作成の様邸は、見積書に行を入れるまで請求書に入れない（`calc.ts` の `startEstimate`）。行がないうちは「笹岡工務店の請求書に入れる」のチェックを出さず、「🛒 発注書を作成」も押せない（`hasEstimateRows`）。
  前から行のある見積書を直しても請求する月は変わらない。ブラウザのテストで新規作成してから見積書を打つときは、「📋 工事見積書」のタブを押す（新規作成は住宅改修申請書のタブで開く）。請求書のチェックを見るのは行を入れてから。
- **写真はこの端末だけ（IndexedDB の `taiyo-sasaoka-photos`）。** 様邸には写真の番号（`Place.photos`）だけを持つので、バックアップ・ほかの端末には写真は入らない（「この端末にない写真」と出る）。

  ほかのセッションが今なにをしているかを見て、`send_message` で分担（誰がどのファイル・どの画面・ポータルのどのフォルダと index.html を持つか）を決める。
  この日は、介護保険証の読み取りを二重に作りかけ、「タブの横に置く・Ctrl+V」は行き違いで2つのセッションが同時に作った（片方を捨てた）。

  （ポータルへの push が重なると、先のデプロイは後のデプロイに置きかわって cancelled になる。後のデプロイに両方入るのでふつうのこと）。
- **iframe で別のアプリ（🛁 特定福祉用具申請書のタブ）を出すときは、枠を消す前に中のアプリの保存を待つ。** 枠を消すと中の IndexedDB の保存が途中で止まり、
  直した値が消えた（`flushTokutei` → 中のアプリの `window.__taiyoTokuteiFlush`。中のアプリの `flush` は保存の途中ならそれも待つ）。
