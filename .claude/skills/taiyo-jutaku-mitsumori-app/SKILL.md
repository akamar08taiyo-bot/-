# 住宅改修 見積書・請求書アプリ（太陽シルバーサービス 行橋営業所）

介護保険の住宅改修で、営業所が作る見積書・笹岡工務店からの仕切り計算・1か月分の御請求書・部材の発注書を1つのアプリで作る。
ユーザーは行橋営業所の担当者（プログラマーではない）。スマホとパソコンの両方で使い、スクリーンショットに丸を付けて「ここを〜に」と頼んでくる。
このスキルは、2026年10月のセッションで積み上げた知識（何をどこで直すか・業務の決まり・確かめ方・公開の仕方・同じ失敗をしない工夫）をまとめたもの。
ポータル全体に共通のこと（アプリの一覧・公開の流れ・ユーザーの好み・報告のしかた）は `taiyo-portal` スキル、Excel の作り方と確かめ方（XSD・LibreOffice のスクリプト）は `taiyo-excel-export` スキルにある（入っていれば一緒に読む）。

## 仕事の進め方

1. **依頼を業務の言葉で読み解く。** 短い文とスクリーンショットで来る。例に計算の書き違いがあることもある（発注書の例「0.15本×2＋0.4本 → 2000mm を1本」は合計 0.7本＝2800mm で 2000mm に入らない）。
   その場合は、例の意図（少なければ 2000mm）を一般のルールにして作り、報告で「こう解釈した」と書く。細かいことを何度も聞き返すより、筋の通った解釈で進めて見せる方が喜ばれる。
   ただし、データを消す・外に送るなど取り返しのつかないことは確かめてから。
2. **関係する所をまとめて洗い出す。** 「当然、請求書や申請書にも転記する」のように、1つの直しがほかの出力（見積書の画面・印刷・Excel・仕切り計算表・請求書・発注書・販売受注簿）にも届くことを期待されている。
   直す前に `grep` で同じ値を使う所を全部見る。
3. **小さく直し、まわりのコードの書き方に合わせる。** コメントは日本語で「なぜ」を書く（このリポジトリの流儀）。画面の文字は短く、やさしい言葉で。
4. **確かめる。** 単体テスト・型チェック・ブラウザのテスト（Playwright）を通し、見た目を変えたらスクリーンショットを撮って自分の目で見る。スマホの幅（390px）も見る。手順は `references/build-test-publish.md`。
5. **公開する。** ユーザーが「公開して」と言ってから（本番。作業環境の安全確認で止められたら回り道をせず、ユーザーに聞く。`taiyo-portal` スキル）。
   2つのビルド（`build:sasaoka`・`build:jutaku`）の `index.html` と `version.json` を taiyo-portal の2つのフォルダに置いて push。ポータルのタイルの使い方の文（`taiyo-portal/index.html` の `APPS`）も、変えた所に合わせて直す。
6. **デプロイを確かめる。** github.io はこの作業環境から見えないので、GitHub MCP の `actions_list`（`pages build and deployment`）で success を見る。
7. **報告する。** 日本語・やさしい言葉で、①できたこと ②使い方（番号付き） ③確かめてほしいこと（解釈したところ・ユーザーのデータに要るもの） ④テストと公開の結果。スマホで古い画面が出たら上の「⟳ 読み込み直す」を押すように添える。

  新しく画面の文を足すときも「笹岡」と書かない（e2e-estimate で施工費のマスタに「笹岡」が出ないことを見ている）。
- 言葉：「工賃」ではなく「**施工費**」。「一式」ではなく「**部材＋施工費（常用）**」。「手摺」ではなく「**手すり**」（2026-10。施工費・取り込む商品名・申請書とも。`util.ts` の `tesuri`）。
